## What it describes

```
VPC 10.20.0.0/16, 3 availability zones
├── public subnets     load balancers, NAT gateways
├── private subnets    EKS managed nodes (outbound through NAT, S3 through a gateway endpoint)
└── data subnets       MSK, RDS, ElastiCache. No route to the internet.

KMS          one customer-managed key, rotated yearly
EKS          private API endpoint, secrets encrypted, control-plane logs, IMDSv2,
             VPC CNI with network policy enforcement, OIDC provider, workload role
MSK          3 brokers, encrypted storage, encrypted traffic between brokers, no public access
RDS          PostgreSQL 16, Multi-AZ, encrypted, TLS enforced, master password in Secrets Manager
ElastiCache  Redis 7, 2 nodes with failover, encrypted at rest and in transit, AUTH token
S3           private, versioned, SSE-KMS, TLS only, lifecycle to colder storage
```

|---|---|---|

| vpc | `modules/vpc` | VPC, 9 subnets, NAT, routes, S3 endpoint, flow logs |

### Security properties, as written

- **Encryption at rest**: RDS storage, backups and Performance Insights; MSK
  broker volumes; ElastiCache; S3 objects; Kubernetes secrets in etcd;
  CloudWatch log groups; Secrets Manager secrets. All with the customer-managed
  key. Node root volumes are encrypted with the account's default EBS key.
- **No public database endpoint**: RDS has `publicly_accessible = false`, MSK
  has public access disabled, and all three stores sit in subnets without any
  route to the internet. They accept connections from the security group of
  the EKS nodes only.
- **The Kubernetes API is private** by default.
- **No password in a variable**: RDS generates the master password. The Redis
  AUTH token is generated by Terraform and is therefore in the state, which is
  why the state must be encrypted (`backend.tf`).
- **Tags**: `Project`, `Environment`, `ManagedBy`, `Repository` on everything,
  through the provider's `default_tags`.

## Use

```sh
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars      # adjust
# configure remote state first: see backend.tf
terraform init
terraform validate
terraform plan -out plan.tfplan
terraform apply plan.tfplan

terraform output -json helm_values                 # non-secret values for the chart
```

Then create the Kubernetes Secret from the two Secrets Manager secrets
(`postgres_master_secret_arn`, `redis_url_secret_arn`), and install the chart
(`infra/helm/rosetta/README.md`).

## Where the application and AWS do not fit yet

These are limits of the application code, found while writing this. They are
not hidden by the Terraform, and each one decides a setting here.

1. **TimescaleDB is not available on Amazon RDS.** `infra/sql/postgres_extras.sql`
   detects that and creates `telemetry` as a plain table. On RDS, run Rosetta
   with `ROSETTA_TELEMETRY_STORE=parquet` (the `helm_values` output does), which
   makes the Parquet archive in S3 the history. To keep the hypertable,
   compression and the continuous aggregate, use Timescale's managed service
   or run TimescaleDB yourself, and drop the `rds` module.
2. **The Kafka client cannot use TLS or authenticate.**
   `rosetta/adapters/kafka_broker.py` passes only `bootstrap.servers`. MSK is
   therefore created with `TLS_PLAINTEXT` and unauthenticated access, protected
   by security groups and private subnets. Traffic between brokers is
   encrypted, traffic between Rosetta and the brokers is not.
3. **The application creates topics with replication factor 1.** The Helm
   chart creates them first, with replication factor 3.
4. **The object store client needs static access keys.**
   `rosetta/factory.py` always passes `ROSETTA_S3_ACCESS_KEY` and
   `ROSETTA_S3_SECRET_KEY` to pyarrow, even when they are empty, so the
   credentials of the workload role are never used. The role and its policy
   are created here because that is the right design, but today Rosetta needs
   an IAM user with the policy `module.s3.access_policy_arn` and its access
   key in the Kubernetes Secret. This configuration does not create that user,
   because its secret key would end up in the state.

## The same Helm chart on GKE or AKS

Being cloud-agnostic is a requirement of the project. The split is: everything
Rosetta-specific lives in the image and in the Helm chart, and neither contains
anything about a cloud. Terraform is the only part that is written per cloud.

### What does not change

| Piece | Why |
|---|---|
| The container image | one image, configured by environment variables only |
| The Helm chart templates | plain Kubernetes API: Deployment, Job, Service, Ingress, HPA, PDB, NetworkPolicy |
| The names of the settings | `rosetta/config.py` reads the same variables everywhere |
| `infra/sql/postgres_extras.sql` | detects which extensions the server offers |
| Prometheus rules and the Grafana dashboard | they read Rosetta's own metrics |
| `docker-compose.yml` | the same stack on one machine |

### What changes

Only values, and the Terraform underneath.

| Concern | AWS (this directory) | Google Cloud | Azure |
|---|---|---|---|
| Kubernetes | EKS | GKE | AKS |
| Kafka | MSK | Managed Service for Apache Kafka, or Strimzi in the cluster | Strimzi in the cluster, or Confluent Cloud |
| PostgreSQL | RDS | Cloud SQL, or AlloyDB | Azure Database for PostgreSQL flexible server |
| Redis | ElastiCache | Memorystore | Azure Managed Redis |
| Object store | S3 | Cloud Storage, through its S3-compatible XML API with HMAC keys | Blob Storage, which has no S3 API |
| Keys | KMS | Cloud KMS | Key Vault |
| Secrets | Secrets Manager | Secret Manager | Key Vault |
| Workload identity | IRSA: `eks.amazonaws.com/role-arn` | `iam.gke.io/gcp-service-account` | `azure.workload.identity/client-id` |
| Ingress | AWS Load Balancer Controller or ingress-nginx | GKE Ingress or ingress-nginx | Application Gateway or ingress-nginx |
| NetworkPolicy enforcement | VPC CNI with network policy enabled | Dataplane V2 | Azure CNI with Cilium or Calico |

Values that differ per cloud:

```yaml
# GKE
config:
  ROSETTA_KAFKA_BOOTSTRAP: "kafka.example.internal:9092"
  ROSETTA_S3_ENDPOINT: "https://storage.googleapis.com"
  ROSETTA_S3_BUCKET: "rosetta-telemetry"
  ROSETTA_TELEMETRY_STORE: "parquet"          # Cloud SQL has pgvector, not TimescaleDB
serviceAccount:
  annotations:
    iam.gke.io/gcp-service-account: rosetta@example-project.iam.gserviceaccount.com
ingress:
  className: nginx
```

### What is honestly unsolved on the other clouds

The table above is the plan. None of it has been deployed, on any cloud. The
points below would need work, and they are all in the application, not in the
chart:

- **Managed Kafka with mandatory authentication.** Google's managed Kafka and
  Azure Event Hubs (Kafka endpoint) accept only authenticated TLS connections.
  Rosetta's Kafka client cannot do that yet, so on GKE and AKS the realistic
  choice today is Strimzi inside the cluster with an internal plain-text
  listener. Adding `security.protocol` and SASL settings to `KafkaBroker`
  removes the limit on all three clouds.
- **Azure Blob Storage has no S3 API.** The archive adapter speaks S3 only.
  Azure needs either an S3 gateway in front of Blob Storage or a second
  adapter built on pyarrow's `AzureFileSystem`. The port for it exists
  (`rosetta/ports/stores.py`), the adapter does not.
- **Cloud Storage through the S3 API** works with HMAC keys for the calls
  Rosetta makes (put, get, list, copy, delete), but it has not been tested.
- **TimescaleDB** is offered by none of the three managed PostgreSQL services
  with its full feature set. Azure offers the Apache-licensed edition, which
  lacks compression and continuous aggregates, so `postgres_extras.sql` would
  stop at the compression step there. Use `ROSETTA_TELEMETRY_STORE=parquet`,
  or a TimescaleDB you operate.

A Terraform configuration for GKE or AKS would have the same seven modules
with the same outputs (`kafka_bootstrap_brokers`, `postgres_endpoint`,
`redis_endpoint`, `archive_bucket`, `workload_role_arn`, `helm_values`), so the
step from Terraform to Helm stays identical. It has not been written.
